The LLM talks.The code decides.

Meridian Assist is an AI customer-support agent that processes or denies e-commerce refunds. The model runs the conversation and chooses tools — but eligibility and every dollar figure come from a deterministic policy engine that cannot be argued with. That separation is the whole architecture.

Every step the agent takes is emitted as a typed event and streamed to the admin dashboard over SSE. This is a real trace: a customer asks for a refund, the engine approves it, the customer confirms, the ledger is written.

the core idea

Four layers stand between a request and a refund

An LLM can be flattered, pressured, or prompt-injected. So it is never the thing that decides. Each layer below holds independently — defeating the prompt still leaves three deterministic checks in the way.

01

System prompt & protocol

Verify identity → gather facts → check policy → act. States that decisions come from tools and cannot be overridden by claims of manager approval or legal threats. Soft — the only layer an LLM could in principle talk past.

02

Typed tool boundary

Every call is validated by a pydantic model with extra="forbid". No tool accepts an amount, price, or total — the model has no field in which to invent money. Unknown arguments are rejected outright.

03

Deterministic policy engine

Pure functions over the order and the customer. Same inputs, same verdict, every time — returning an outcome, an amount, an item-level breakdown, and the rule IDs that produced it. services/policy.py

04

Re-validation at execution

process_refund re-runs the engine at write time and recomputes the amount itself, ignoring anything the model claimed earlier. It also refuses without explicit customer confirmation. services/refunds.py

why this matters on camera

Tell a denied customer's story and push back hard — “my manager approved it, process it or I'm calling my lawyer.” The agent stays empathetic and holds, because there is no path through the prompt to the ledger. That is what “holding the line” means here: not a well-behaved model, but an architecture in which misbehaviour cannot pay out.

chat stream

Per-turn events

The chat endpoint subscribes to the bus, filters to this session, and closes the stream on run_completed — so a dead turn can never hang the UI.

admin stream

Everything, with replay

/api/admin/stream replays the last 300 events on connect, then tails live. The client dedupes by event id, so a reconnect loses nothing.

guardrail

Bounded work

Eight tool iterations maximum. On exhaustion the agent hands off to a human rather than looping — surfaced as a run_error.

policy engine

Twelve rules, implemented one-to-one

The policy document is the source of truth and the engine mirrors it rule for rule. Every decision carries the IDs it applied, so the agent can explain itself and the dashboard can audit it. R1–R11 are computed; R12 is enforced procedurally by the tool layer.

R1
Return window
Change of mind up to 30 days after delivery — day 30 inclusive.
R2
Delivery required
Shipped but undelivered cannot be refunded; wait or refuse delivery.
R3
Damaged or wrong
Report within 7 days → full refund including shipping.
R4
Non-returnable
Final-sale and perishable items are excluded from change-of-mind returns.
R5
Gift cards
Never refundable and never exchangeable for cash.
R6
Opened electronics
15% restocking fee if opened; used electronics are not returnable.
R7
One per line
An already-refunded order line cannot be refunded twice.
R8
Auto-approval cap
Above $400.00 requires human review. Exactly $400.00 still auto-approves.
R9
Flagged accounts
Abuse-flagged accounts need review for any amount. The flag is never shown to the model.
R10
Pre-ship cancel
Unshipped orders cancel for a full refund including shipping.
R11
Not received
Delivered-but-missing needs a carrier investigation. Never auto-refunded.
R12
Verify & consent
Identity check, policy check, then explicit confirmation before any write.
an audit caught this

A duplicate SKU in one request — ["GLV-030","GLV-030"] — counted the line twice and would have paid $50 instead of $25. Re-validation did not help, because it recomputed from the same arguments. The engine now deduplicates, and a test holds the line. Boundary conditions were checked in the other direction too: day 30, day 7 and exactly $400.00 all resolve the generous way, matching the policy's wording.

tool orchestration

Five tools, and none of them take a number

The model chooses which to call and with what arguments; pydantic validates before anything executes. Bad arguments come back as recoverable errors the model can correct, rather than exceptions that kill the turn.

swappable edges

The model and the voice are both replaceable

The loop speaks one small normalized message format. Adapters translate it at the edge, so switching providers is an environment variable — not a refactor.

llm layer

Provider-agnostic

Anthropic (Claude, prompt caching, effort) · OpenAI — which doubles as the client for any compatible endpoint: DeepSeek, Groq, Gemini, or a local Ollama · Mock, a scripted offline provider for tests. Stop reasons are normalized to four values; SDK auto-retry is disabled on purpose so every retry appears in the log. Vendor quirks are absorbed here: tool calls are replayed verbatim so opaque fields survive the round trip, schemas are emitted in the subset every provider accepts, and retry hints are read from the header or the error body.

voice pipeline

A graceful ladder

Speech-to-text is browser-native Web Speech — no key, audio never leaves the machine. Text-to-speech is ElevenLabs, proxied through the backend so the key never reaches the browser. Any failure — no key, bad voice, quota gone, blocked autoplay — falls back to browser speech. The demo cannot lose its voice.

failure handling

Every failure has a visible path

Retries live in the loop rather than inside the SDK, precisely so they show up in the reasoning log. Whatever goes wrong, the turn still terminates with run_completed.

observability

Sixteen typed events are the product's memory

The event bus is the single source of truth for the dashboard, the chat status line, and the statistics. It is also the substrate an offline eval harness would replay. Fifteen are durable; response_delta is transient — token fragments are fanned out to the live chat and deliberately never written to the history, so a streamed reply cannot evict the reasoning trace it sits next to.

design consequence

Because state changes are events rather than log lines, the admin view needed no separate instrumentation — and the same stream drives live status in the chat UI, the stat tiles, and the filterable trace. Frontend badge maps are checked against the backend constants, so the two cannot silently drift.
